# Research Findings: URL Hash and `logoversion` Web Edition Defect

**Status:** Reproduced and contained
**Researched:** 2026-11-22 (UTC)
**Question:** Can URL hash or search parameters reach the Web Edition terminal output for `logoversion`, and could tainted URL content reach Logo data, parsing, evaluator state, or JavaScript self-evaluation?
**Scope and assumptions:** Initial read-only repository trace on branch `wasm`, followed by a live Chrome reproduction and a temporary `--emrun` disable for the Web HTML target. Browser search-parameter reproduction was performed after the user supplied the production URL. Decomposition count: 0.

## Follow-up Note

Logo handles command-line arguments in an unusual way that probably contributed to URL data leaking into terminal behavior. When work on URL-driven startup resumes, investigate the `webmain.c` argv/file-loading and `command.line` split first, including the `-` separator convention and delayed/error output behavior. This issue is temporarily contained by disabling all Emscripten browser URL-to-argv handling; do not restore it until a secure design has explicit parsing, allowlisting, and tests.

## Key Findings

1. `logoversion` is initialized directly as the numeric Logo value `6.2` in both Web and native startup, rather than from browser URL state. It is registered as a buried variable and should print as a real number. [E1, E2]
2. URL **hash** text is not found in the Logo startup or runtime flow. Source reads `window.location.hash` only for an exact `#viewport-debug` UI diagnostic gate. Other text in the hash does not affect Logo. [E3]
3. URL **search** text, which is distinct from hash text, is read by the Emscripten-generated loader: it is split on `&`, decoded with `decodeURI`, and placed in `Module.arguments`. This is the loader-to-argv boundary, not an immediate Logo command or expression path. [E4]
4. `Module.arguments` becomes process argv and is converted by `webmain.c` into the buried `command.line` list, with behavior controlled by the argv `-` separator convention. It is not assigned to `logoversion`, supplied to `runjs`, or fed directly to the parser/evaluator. [E5]
5. Hash/search content can reach Logo only through an existing startup procedure that explicitly consumes `command.line`, or through some separately observed code path not present in source search. No such web startup consumer was found. [E6, E7]
6. The JavaScript `runjs` bridge does support evaluation of JavaScript expressions and uses `eval` or `new Function`. However, URL arguments are not observed entering this bridge, and existing tests establish that hostile strings passed as bound `runjs` parameters remain data rather than changing the expression source. [E8, E9]
7. The reported hash-to-`logoversion` output relationship is **not supported by the inspected code**. The strongest evidence is for a stale/generated-artifact or reproduction mismatch, a live runtime mutation of `logoversion`, or an external browser extension/intermediary, not a direct hash-input defect.

## Future Research Notes

- Logo handles command-line arguments in a non-obvious way that may explain how this input leaked into version output. Investigate Logo's command-line argument consumption first when this work resumes.
- Regardless of the outcome of passing command-line arguments through URL hash parameters, using URL hash parameters to pass environment-like variables may still be useful. Evaluate that idea later with an explicit allowlist, decoding policy, injection-resistant transport, and clear separation from executable input; do not conflate environment data with argv or Logo source.

## Options and Trade-offs

- **Containment: reject URL args before runtime startup.** Clear or restrict `Module.arguments` for browser loads, preserving only explicitly supported options. This reduces command-line exposure but could break undocumented URL invocation conventions.
- **Containment: isolate hash handling.** Do not read or interpolate `location.hash` anywhere except the exact viewport diagnostic check, and ensure the viewport mode does not construct executable Logo or JavaScript strings.
- **Final fix: trace the observed malformed output.** Before changing Logo code, verify the running `logoversion` value, `command.line`, page URL, JS global state, startup procedure, service worker, and page source/hash. Hash text alone is not sufficient evidence to modify the primitive.
- **Final fix: preserve data/statement separation in `runjs`.** If URL-derived values are ever used, continue passing them as bound arguments; never concatenate them into expression source. In C, maintain ASCII validation or define and test an explicit Unicode policy.
- **Sanitization policy:** URL-provided text is tainted. Decode only once in a fixed parser, then pass values as opaque data. For percent-encoded malformed input, handle decoder errors; for Logo text, quote/escape or construct values as NODE strings rather than reparsing text; for HTML/DOM output, use text nodes or framework-safe APIs; for JavaScript, use bound parameters or JSON serialization rather than `eval`/`new Function` string concatenation.

## Conflicts and Counterevidence

- The confirmed defect request says URL hash parameters appear in `logoversion` output, but source contains no hash-to-variable assignment or hash-to-output code.
- Search parameters are confirmed to affect argv, but not hash. An attacker-controlled hash remains browser-side and does not enter the server or Emscripten loader in normal navigation.
- Native targets have no browser URL parsing and should not receive hash data. Native could still be affected only if an external launcher supplies equivalent argv values.
- Existing hostile-`runjs` tests reduce confidence that bound parameters create JavaScript expression injection, although expression source injection remains possible whenever application code concatenates controlled text into `expr`.

## Constraints and Dependencies

- Stale `ucblogo.html`, `ucblogo.js`, `ucblogo.wasm`, or `sw.js` could contradict source. HTTP cache and service-worker cache must be ruled out before implementation.
- `logoversion` is buried/val-only in startup but any active Logo procedure could assign or otherwise manipulate variables depending on Logo semantics. Verify the actual runtime value rather than assuming initialization alone.
- Self-evaluation requires a control path that sends tainted text into `runjs` expression source or another parser/evaluator entry. No current evidence shows URL hash/search doing that.

## Unknowns and Unverified Items

- Exact URL/payload used for the confirmed reproduction.
- Whether `logoversion` is visibly numeric but polluted through concatenation in output or startup code.
- Whether a browser service worker or generated loader differs from checked source due a stale deployed artifact.
- Whether startup or persistent procedure state is modified in the user's browser/IDBFS.
- Whether query and hash are accidentally conflated by a hosting redirect or test fixture.
- Browser and JS-engine behavior for malformed percent sequences under `decodeURI`.

## Search Coverage and Limitations

Searched exact and alternate symbols and URL APIs across source, tests, and generated Web artifacts. Searches included `logoversion`, `LogoVersion`, `location.hash`, `location.search`, `window.location`, `URLSearchParams`, `Module.arguments`, `decodeURI`, `decodeURIComponent`, `lrunjs`, `runjs`, `eval`, `new Function`, `CommandLine`, `Startup`, and startup loading. The broadest workspace search was bounded by source/test/generated paths and did not execute a browser or send external requests. Unsearched external browser state and deployed PWA caches remain unknown.

## Options and Trade-offs

The smallest defensible containment is to document URL arguments as untrusted and verify no startup procedure or `runjs` expression consumes them. The smallest final fix, if reproduction proves runtime mutation, should be at the actual mutation boundary: remove or sanitize the data source, or reset/validate `logoversion`, rather than changing the numeric primitive to defensively coerce browser input.

The cheapest regression seam is an acceptance fixture at the URL/page-load boundary:

- Open the Web Edition with a representative hash and search payload.
- Assert the `logoversion` result equals `6.2` and `logoversion` remains numeric.
- Assert the hash does not alter `command.line`, startup variables, or browser globals.
- Assert hostile search text remains bound argument data if a URL-driven startup bridge is intentionally supported.
- Keep a separate narrow unit test for `runjs` expression-vs-bound-parameter separation.

## Planning Handoff

The planning agent should treat hash and search as separate trust boundaries. It should first reproduce in a fresh runtime and capture URL, `logoversion`, `command.line`, startup procedure state, generated artifact hashes, service-worker control, and cache settings. If no mutation is reproducible, classify the issue as stale/reproduction state rather than a code-injection defect. If mutation is reproduced, plan an instrumentation-only trace from page load through argv, startup parsing, variable assignment, and output, then the smallest fix at that boundary.

## Stale-Artifact Checks

For the original reproduction, verify the served URL and running HTML/JS/Wasm provenance; disable HTTP cache and bypass/unregister the PWA service worker during diagnosis without clearing unrelated storage; reload or close/reopen the controlled tab; preserve IDBFS/editor work; and compare actual served content/hashes with the checked `wasm` source. This is especially important because source and generated `ucblogo.js`/`ucblogo.html` currently differ by build generation format.
