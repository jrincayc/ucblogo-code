## Goal

Provide a fast, flat, risk-proportionate software-development workflow that catches defects at the earliest useful check, supports ordinary implementation iteration, and prevents defects that escaped a gate from moving farther downstream. The six-stage flow is the default path, not a mandatory fit for every task. For tasks using it, the stages remain sequential and independent work may run only within the currently approved stage. A task-specific deviation requires explicit user approval, stays within its stated scope, and is recorded; similar or recurrent deviations prompt a user-owned workflow-update proposal instead of repeated waivers. The orchestrator decomposes standard-path work into bounded tasks and assigns each directly to an agent. Agents do not delegate to other agents. Keep the workflow usable under slow or interrupted networking and the user's stated workstation limits.

## Workflow Requirements

1. Use Research -> Plan -> Test Plan -> Implement Tests -> Implement Changes -> Code Review as the default risk-proportionate path, not a mandatory fit for every task. When using the standard path, keep stages sequential, with a defined deliverable, independent QA verdict, and explicit human approval before advancement. A failed gate blocks advancement but can be repaired within its approved scope. A custom role may propose, but cannot authorize, a departure; the user must explicitly approve the particular rule or step, scope, rationale, and limits. A generic task request does not waive later gates. Record approved deviations in the task workflow-run record and label each skipped gate "not run under approved deviation," never PASS. Preserve separate, fresh, exact-scope user approval after post-commit QA/review and before every push.
2. In Test Plan, prepare a handoff-ready specification for test implementers: acceptance criteria, cases and scenarios, inputs and expected results, environment, setup/teardown, focused commands, regression scope, and relevant negative cases. Create compact, deterministic mock/fixture data, builders, or seeds when useful; otherwise explain why fixtures are unnecessary. Keep fixtures local and free of secrets or unnecessary sensitive data. Test implementers follow the approved specification and raise coverage changes for approval.
3. During Research, classify visual impact and have QA verify any not-applicable decision. For visual work, `Development Design Reviewer` reviews proposed screens/mockups and affected states before Plan approval and advancement to Test Plan; QA verifies the exact artifacts and criteria coverage, and the human approves. After implementation, the reviewer inspects actual rendered output and interactions at agreed desktop/mobile viewports and relevant states before advancement to Code Review; QA verifies artifact/revision identity and criteria coverage, and the human accepts. Missing visual evidence blocks advancement. A nonvisual task records a QA-verified not-applicable result.
4. Preserve normal iteration only for expected failures that reveal no defect or blocking abnormality: a failed sketch, expected-red test, or unsuccessful bounded attempt is recorded, diagnosed, and retried within the approved scope. Three consecutive unsuccessful attempts on the same issue trigger Andon. Evidence of a defect, blocking abnormality, exceeded authority, or uncertainty about whether a blocker exists triggers Andon immediately.
5. Andon means **all work stops immediately**, including the discovering and potentially involved agents: all tasks, parallel branches, builds, tests, POCs, commits, and stage advancement pause while state is preserved. QA and the supervisor triage the evidence and report findings, options, and risks to the user; the user performs independent triage. The user may invite agents into collaborative resolution planning outside the normal stage workflow. Seek consensus; if it is not reached, the user makes the final decision. Planning does not authorize implementation. The user must explicitly authorize implementation and specify its resume stage; ask if no stage is named. Implementation then resumes only for the user-authorized scope at that stage, while all unrelated work remains paused. Global resumption requires a committed fix, passing focused validation and independent QA/review, recorded evidence, and the user's explicit clear-to-resume. A procedural QA failure with no suspected defect or blocker is a local gate hold, not Andon.
6. After each semantic block, the assigned owner runs a focused self-check, stages only task-owned paths, inspects the exact staged diff, and commits promptly. The local commit is not blocked by prior reviewer, QA, or human approval. Independent code/design review and QA happen after the commit, use its exact hash, and record QA verdicts/findings against that hash. FAIL or BLOCKED blocks dependent work and stage advancement, not the owner's in-scope repair commits. Keep commits small and frequent. Prefer shared task integration with disjoint file ownership and serialized Git-index operations; avoid simultaneous same-file edits, integrate small commits promptly, and run focused checks after integration. Use isolated worktrees/build directories when files overlap or build state is incompatible. All roles may run bounded task-scoped POCs in isolated state; record path, command, outcome, and limitations in durable evidence; POCs are not acceptance. On the standard path, request stage approval after relevant commits and post-commit QA/review, before advancement. For every push, require separate, fresh, explicit user approval naming the exact remote, destination branch, and commits or range after post-commit QA/review and before pushing; stage approval does not imply it. Do not rewrite pushed history.

7. Similar or recurrent user-approved task deviations trigger a proposed workflow update for the user to consider; they are not normalized as repeated waivers. The user owns changes to the default process.
8. Use the Worker pool for independently verifiable implementation slices when useful; keep direct assignment, dependency, scope, and active-instance limits explicit. Allow open-door peer questions without allowing peer task assignment. Escalate unanswered questions and raise Andon when no available agent can answer. Maintain recurring answers in the Agent FAQ. CTO Research/Plan input is advisory; final language review is independent and exact-hash. CTO/QA spot-checks are narrow, risk-based supplements, not duplicate QA cycles.

## Process Deviation Requests

Agents may request process deviations, especially for process improvement or defect resolution, but a request is not an exception. The human project maintainer must review and explicitly approve the particular rule, scope, rationale, and limits before any action departs from process. Requests identify the default rule, proposed change, evidence, benefits, risks, alternatives, validation/rollback, and gates affected. Record the decision before acting. An Andon stop remains active until the user authorizes its scoped resolution at a named resume stage; deviations never waive separate push approval.

## Code Review Retrospective

Before final Code Review-stage approval, the Orchestrator gathers a short reflection from every participating agent and facilitates an active discussion with the human maintainer. Cover process, successes, improvement ideas, process deviations, and Andon events. Record the human's input, proposals, and dispositions in the task record. Recommendations do not authorize policy changes, and a retrospective never clears an active Andon.

## Direct Assignment, Network, and Resources

- Use GPT-6 Luna at maximum supported reasoning effort for every role unless the user specifies or approves an alternative. Disclose unavailable settings and never silently substitute. The orchestrator directly assigns each bounded task to a fresh agent instance. Each agent instance receives exactly one task assignment and is retired when that assignment completes; never reuse it for another task. Each assignment prompt must request maximum reasoning effort and include scope, ownership, acceptance criteria, checks, return format, and applicable repository instructions. Maintain a task ledger with a unique ID, owner, dependencies, and status for every assignment. Parallelize only distinct, dependency-ready tasks within the currently approved stage; never assign the same task ID to more than one agent at a time. Agents cannot launch, invoke, or delegate work to another agent. Route follow-on work requests back to the orchestrator for a separate direct assignment to a fresh agent instance. If no eligible agent or required model is available, mark the task BLOCKED, hold dependent work and stage advancement, and request human direction; do not use nested delegation or silently substitute an owner or model.
- Optional parallel map/reduce pattern: when useful, the orchestrator may split work into distinct map tasks, enqueue dependency-ready tasks, and directly assign each to a fresh agent instance. As map results arrive, it may create reduce tasks over explicitly defined subsets of those results and assign each reduction to a different fresh agent instance; independent reductions may run concurrently. Further or final reductions can be scheduled the same way after their dependencies are ready, each with a fresh agent instance, or handled by the orchestrator. Track map and reduce tasks in the same ledger and dependency graph, with explicit inputs and output contracts. The orchestrator owns scheduling and checks that results are complete and compatible. Limit concurrent assignments to available resources, retiring each worker after its single task rather than reusing it for later work. This is a scheduling option, not a requirement; use a serial path when partitioning or coordination would not help. All assignments remain direct, and no agent launches another agent.
- Soft I/O scheduling preference: when it is obvious that several tasks will compile or build concurrently, stagger their starts when practical (for example, tests that each trigger a compilation) to reduce I/O contention. This is not strict serialization; overlap is acceptable when the expected penalty is small or delaying work costs more.
- Prefer approved cloud-hosted agents for eligible independent research, planning, test, implementation, and review work. Keep local-only runtime, browser/device, or hardware checks local when cloud agents cannot access the same environment. Transfer only necessary prompts, diffs, and compact test artifacts; reuse cached data and avoid duplicate uploads. Never transmit secrets to unapproved services. Do not claim cloud delegation ran unless it did.
- On a detected network interruption, pause all task work, local and cloud, at a safe checkpoint and preserve in-progress state. Resume only when passive recovery is indicated, a necessary ordinary network operation succeeds, or the user confirms recovery. Do not generate traffic solely to test connectivity. Record the pause, recovery signal, and resume point; do not claim remote checks passed while unavailable. During ordinary slowness, avoid unnecessary requests and duplicate transfers.
- User-provided workstation profile: quad-core Intel i7, 32 GB RAM, 1 TB disk. Treat these as total capacities, not available headroom. Check current CPU, free memory, and disk for heavy work when observable; cap CPU-heavy concurrency at four cores and reduce it to preserve responsiveness or when resources are constrained. If resource data is unavailable, state that and schedule conservatively.

### Integration, commit, and rollback

P1 and P2 may proceed as independent implementation-stage tasks only after the Plan stage is approved; assign disjoint file ownership and do not edit the same file concurrently. P3 follows both. P4 is optional learning and never blocks P5, which follows static validation. Prefer one shared task integration branch/worktree for disjoint files and serialize Git-index operations; use isolated worktrees/build directories when ownership overlaps or build state is incompatible. Each assignee commits its own task-scoped changes after focused self-check and staged-diff inspection. QA and review occur after commit against its exact hash; FAIL/BLOCKED blocks dependent work and stage advancement, not owner repair commits. Run focused checks after integration.

If a focused check fails or post-commit QA/review rejects a substep, keep dependent work at the current gate and repair only within the approved scope; the owner may commit repairs without waiting for QA approval. Re-check and obtain fresh post-commit review/QA for each repair commit. If a change must be backed out, revert only the task-owned commit(s) after preserving unrelated work; do not rewrite history. A defect discovered after a passed gate reopens that gate and blocks affected downstream work under the shared contract.
